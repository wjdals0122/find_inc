# 스킬 산출물 GitHub Push

## 적용 범위

`/brand`, `/product`, `/competitor`, `/customer`, `/marketing-brief`, `/strategy-dashboard`가 산출물을 생성하거나 수정하면 검증 후 GitHub에 커밋과 push까지 수행한다. 사용자가 해당 작업에서 push하지 말라고 명시하면 그 지시를 우선한다. 산출물 변경이 없는 탐색·추천·대화 답변에는 적용하지 않는다.

## 절차

1. 작업 시작 전에 `git status --short --branch`, 현재 브랜치, upstream과 원격 주소를 확인한다. 기존 커밋과 staged·unstaged·untracked 변경을 파악하고 보존한다. 산출물은 사용자가 지정한 저장소와 경로에 작성한다.
2. 해당 스킬의 산출물 검증을 완료한다. 문서, 에셋, 출처·수집 기록, 대시보드 등 이번 요청을 완료하는 데 필요한 파일을 식별한다. API 키, `.env`, 쿠키, 임시 파일과 사용자 원본을 잘못 포함하지 않는다. 기존 개인정보 보호·재사용 권한 규칙을 따른다.
3. 변경 내용을 검토한 뒤 대상 경로를 명시해 stage하고, 이번 작업의 파일만 커밋한다. `git add .`나 `git add -A`로 무관한 변경을 포함하지 않는다. 기존 staged 변경도 임의로 커밋하거나 해제하지 않는다. 같은 파일에 기존 변경이 섞였다면 해당 변경을 보존하며 이번 작업 부분만 분리한다. 분리할 수 없으면 이유와 필요한 정보를 알린다.
4. 실제 변경을 설명하는 메시지로 커밋한다. 다른 스킬을 하위 절차로 호출한 경우 상위 작업에서 관련 산출물을 모아 한 번 커밋·push해도 된다. 변경이 없으면 빈 커밋을 만들지 않는다.
5. 기존 upstream이 의도한 GitHub 저장소의 작업 브랜치라면 해당 브랜치로 push한다. upstream이 없으면 GitHub 원격과 현재 작업 브랜치를 확인해 `git push -u <원격> HEAD:refs/heads/<작업 브랜치>`로 명시한다. 임의로 `main`에 보내거나 다른 브랜치로 바꾸지 않는다. detached HEAD이면 요청에서 지정된 작업 브랜치를 사용하고, 대상이 불명확하면 필요한 브랜치 정보만 확인한다.
6. push 거절 시 fetch로 원격 상태를 확인한다. 관련 없는 로컬 변경을 보존하면서 원격 변경을 통합할 수 있으면 통합·검증 후 다시 push한다. 강제 push, `reset --hard`, 사용자 변경 삭제로 해결하지 않는다. 인증·권한·브랜치 보호·충돌로 완료할 수 없으면 로컬 산출물과 커밋을 보존하고 실패 이유와 남은 작업을 보고한다. 자격 증명은 출력하지 않는다.
7. 성공 응답과 원격 브랜치의 커밋을 확인한다. 최종 응답에 산출물 경로, 커밋 SHA, GitHub 저장소·브랜치와 push 성공 여부를 알린다. 로컬 저장이나 커밋만 끝난 상태를 push 완료로 보고하지 않는다.

GitHub push는 산출물을 저장소에 반영하는 절차다. 웹 게시, ChatGPT Sites 배포, 광고 집행은 각 스킬의 별도 요청 조건을 그대로 따른다. push 자체에 대한 추가 승인을 상시 요구하지 않는다.

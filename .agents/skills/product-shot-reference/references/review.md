# 결과 리뷰와 사용자 피드백 반영

## 최초 검토

원본 제품·사용한 레퍼런스·결과를 대조한다. 모아보기로 여러 장의 일관성을 확인하고 개별 이미지도 열어 디테일을 검토한다.

| 항목 | 확인할 내용 |
|---|---|
| 제품 일치 | 실루엣, 부품 개수·배치, 색·재질, 로고·라벨, 사용자 수정 참조의 식별 요소 |
| 레퍼런스 반영 | 선택한 구도·분위기·빛, 참고 상품의 형태나 브랜드가 섞이지 않았는지 |
| 사진 완성도 | 접지·그림자·반사·원근, 불필요한 잘림, 왜곡·중복 부품·깨진 글자 |
| 브리프 일치 | 메시지와 장면의 관계, 없는 기능·효과·성능을 사실처럼 표현했는지 |
| 배치 완성도 | 요청 수량, 개별 컷/그리드 구분, 번호·버전, 실제 형식·크기·비율, 원본 보존 |

확인 불가능한 뒷면·내부·작동 상태는 생성된 추정으로 구분한다. 다른 각도의 생성 이미지를 실제 제품의 검증 근거로 쓰지 않는다. 모든 컷이 같다고 보고하기 전에 실제로 달라진 램프·패키지 라벨·부품 같은 차이를 살핀다.

## 피드백을 수정 조건으로 바꾸기

1. 사용자 표현을 짧게 원문으로 기록하고 대상 번호·버전을 연결한다. “밝게”, “너무 다르다”처럼 넓은 표현도 대화·이미지에서 근거를 찾는다. 파일이나 부위에 따라 수정이 크게 달라질 때만 질문한다.
2. **바꿀 것 / 유지할 것 / 확인 기준**을 정한다. “앞부분은 이 사진처럼”이면 앞부분을 새 사진과 대조하되 차체 색·카메라·배경·다른 컷은 유지한다. 새 참조가 다른 모델이면 전체 상품을 몰래 바꾸지 않고 지정 부위에 적용할 범위를 구분한다.
3. “고마워”, “좋아” 같은 호응을 특정 버전의 최종 승인, 원본 교체 또는 배포 허가로 확대하지 않는다. 이전 결정과 충돌하면 가장 최근의 명시적 피드백을 해당 범위에 적용한다.
4. 잘못된 제품·필수 부위·문구 복제·주요 왜곡부터 수정한다. 취향 변화는 사용자 피드백으로, 해상도 선택 불가는 도구 제약으로 구분한다.

## 수정 실행과 비교

- 기존 결과는 편집 대상, 새 이미지는 지정 부위의 참조로 전달한다. 프롬프트에 변경 범위와 유지 조건을 명시한다. 관련 없는 컷까지 일괄 재생성하지 않는다.
- 새 버전으로 저장하고 전후 비교 미리보기 또는 대응 경로를 제공한다. 요청 부위의 개선과 함께 원래 맞던 부분이 달라지지 않았는지도 확인한다.
- 반영이 부족하면 원인을 특정해 추가 수정한다. 새 피드백 없이 같은 지적을 해결하는 추가 생성은 최대 두 차례로 제한한다. 이후에도 불일치하면 현재 결과·남은 문제·필요한 참조나 도구 제약을 알리고 무한 재생성을 멈춘다. 승인된 비용 한도와 사용자 지정 횟수가 있으면 우선한다.
- `수정 필요`, `반영 확인`, `제약으로 미해결`, `사용자 확인 전`, `사용자 승인`을 구별한다. 내부에서 반영을 확인한 것과 사용자 승인은 별개다. 결과 전달을 완료하기 위해 사용자 승인을 강제로 기다릴 필요는 없다.

## 기록 예시

배치의 생성 기록 또는 별도 리뷰 기록에 이어서 저장한다. 상품명·번호·수량을 고정하지 않는다.

```json
{
  "output": "product-shot4.png",
  "feedback": "색은 그대로 두고 배경을 더 밝게",
  "change": ["배경의 밝기"],
  "preserve": ["제품 색·형태", "구도", "라벨"],
  "acceptance": ["기존 대비 밝은 배경", "제품 색 변화 없음"],
  "revision": "product-shot4-v2.png",
  "prompt_record": "실제 수정 프롬프트 또는 그 기록 위치",
  "review": "수정 부위와 유지 조건의 전후 비교 관찰",
  "unresolved": [],
  "status": "사용자 확인 전",
  "user_approval": null
}
```

특정 결과를 사용자가 승인했을 때만 `user_approval`에 그 발언·대상·시각을 기록한다. 다음 수정에는 확정된 유지 조건을 가져오되 다른 상품 전체의 취향이나 회사 규칙으로 일반화하지 않는다.

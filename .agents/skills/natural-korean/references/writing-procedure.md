# 한국어 글쓰기 절차

이 파일은 사람이 읽는 한국어 글을 만들 때 모든 팀원과 AI 도구(Claude Code, Codex, Gemini CLI)가 따르는 작업 순서다.
찾아낼 번역투와 AI 말투, 그리고 고쳐 쓰는 방법 같은 글쓰기 규칙은 이 스킬의 `SKILL.md`에 있다. 이 파일은 누가 쓰고, 어떤 순서로, 몇 번 돌리고, 결과를 어떻게 확인하는지를 정한다. `SKILL.md`와 이 파일이 부딪히면 이 파일이 우선한다.

사용자가 정한 한국어 작성 원칙의 원본은 `references/rules-block.md`이고, 규칙 파일마다 같은 본문이 들어 있다. 절차는 이 파일 한 곳에만 있다.

## 언제 쓰나

사람이 읽고 판단하는 다음 한국어 글에는 모두 이 절차를 적용한다.

- 완료 보고와 진행 보고 같은 중요한 보고
- AskUserQuestion 팝업 바로 앞의 설명, 팝업의 질문과 선택지
- 보고서, 계획, 결정 페이지, 보고 페이지
- 회의록
- 한국어로 쓰는 이슈와 PR 본문
- 길게 설명하는 아티팩트 댓글 답글이나 보고서에 가까운 답글
- 문서와 그 밖의 산출물
- 슬랙으로 보내는 모든 메시지(브리핑, 리포트 요약, 진행 보고, 완료 알림과 오류 알림)
- 리포트와 산출물(보고 페이지, 결정 페이지, 슬랙 메시지, 문서)에 들어가는 모든 글은 제목, 라벨, 칩, 버튼, 표 머리, 툴팁, 안내 문구까지 빠짐없이 이 절차를 거친다.
- 리드나 작업자가 직접 쓴 문구와 스크립트에 넣은 문구도 예외가 아니다.

다음은 이 절차를 쓰지 않는다.

- 짧은 대화 답변(리드가 직접 쓴다)
- 질문에 짧게 답하는 아티팩트 댓글 답글(리드가 직접 쓴다)
- 코드 주석과 커밋 메시지(영어로 쓴다)
- 이미 확정된 문구를 다시 등록하기만 하는 경우
- 사용자 인용(한 글자도 바꾸지 않고 그대로 옮긴다)

## 읽기 쉬운 보고와 알림

- 친절하고 자연스럽고 간결하게 쓴다. 무뚝뚝한 명사형 나열을 피하고, 독자가 알아야 할 결론과 할 일을 먼저 설명한다.
- 보고서도 읽기 편한 문장으로 쓴다. 격식을 지킨다는 이유로 딱딱한 표현을 유지하지 않는다.
- 문장과 표에서 가운데점을 쓰지 않는다. 쉼표, 조사나 별도 항목으로 나눈다. 직접 인용, 고유명사와 코드 원문은 보존한다.
- 사람이 읽는 날짜는 `10월 22일`처럼 쓴다. 연도를 구분해야 하면 `2027년 1월 31일`로 쓴다. 슬랙 제목은 이 형식을 쓰고 본문 날짜는 슬랙 메시지 작성 기준에 따라 `11/20 23:00`처럼 적는다. 파일명, URL, API 값과 원본 자료의 식별자는 바꾸지 않는다.
- `이번 주 확인 3건, 참고 2건`처럼 내용을 읽는 데 도움이 되지 않는 건수 안내는 뺀다. 금액, 마감과 실패 건수처럼 판단에 필요한 수치는 남긴다.
- 파일은 이름에 직접 링크를 건다. 파일 경로를 코드 표시로 감싸서 링크를 대신하지 않는다. 실제로 접근할 수 있는 주소만 쓰며 아직 게시하지 않은 파일을 게시했다고 쓰지 않는다.
- 긴 내용을 모두 글머리표로 늘어놓지 않는다. 짧은 제목, 문단, 목록과 표를 내용에 맞게 쓰고 절 사이에 여백을 둔다.
- 슬랙은 [슬랙 메시지 작성 기준](slack-messages.md)을 함께 따른다. 짧은 알림에도 문체, 날짜, 링크 기준을 적용한다.
- 사실 보존은 값과 의미를 보존한다는 뜻이다. 날짜의 표시 형식, 파일의 링크 표시와 문장 서식은 이 기준에 맞게 고친다.
- 맥락 없는 독자가 읽는 보고서, 계획, 결정 요청, 검토 페이지는 용어 설명보다 저장된 실제 값 한 줄을 표로 먼저 보여 주고 그 표의 칸을 가리키며 용어를 정의한다.
- 설정 안내 문서는 사람만 할 수 있는 일을 "어디서, 할 일, 받는 값 이름, 시간" 열의 표로 쓰고 표의 칸은 40자 안쪽으로 쓴다.
- 설정 안내 문서에서 에이전트가 할 일은 "에이전트가 대신 하는 것" 한 줄로 빼고 링크와 명령은 표 아래 번호 목록으로 모은다.

## 무엇을 읽고 점검하나

- 리포트, 보고 페이지, 결정 페이지, 계획, 문서를 쓰거나 고치는 담당은 길이와 상관없이 `SKILL.md`와 `references/` 전체를 읽는다.
- `references/quick-card.md`와 프롬프트 양식만 읽는 경우는 팝업과 짧은 진행 보고뿐이다.
- 쓴 글에는 `scripts/check-korean.py` 점검 스크립트를 돌린다.
- 하위 에이전트는 스킬 파일을 Read 도구로 끝까지 읽는다.
- 셸 출력은 길면 잘려서 cat으로는 끝까지 읽지 못한다(2026-10-25에 교정자 두 명이 이 때문에 앞부분만 읽었다).
- 하위 에이전트는 보고에 읽은 파일마다 마지막 줄 번호를 적는다.
- 호출한 쪽은 끝까지 읽지 않은 쓰기나 교정을 무효로 보고 다시 돌린다.
- 점검 스크립트가 보고한 줄은 고친 뒤 다시 돌려 남은 것이 없는지 확인한다.

## 절차

1. 사실 목록: 호출하는 쪽(리드 또는 작업자)이 스크래치패드의 파일에 사실 목록을 쓴다. 숫자, 이름, 선택지, 근거 위치(파일과 줄), 사용자 인용을 담는다. 독자가 겪는 일(실패, 비용, 기다리는 시간, 달라지는 점)을 먼저 적고, 각 사실을 주어와 동사가 있는 문장으로 쓴다. 파일 경로와 코드 이름은 "자세히" 부분에만 둔다. 그 분야의 표준 용어를 쓴다(예: "새어 나가다"가 아니라 "유출되다", "조용히 멈춘다"가 아니라 "오류 없이 중단된다"). API 키, 토큰, 웹훅 주소, 앱 암호는 "인증 정보"라고 부르거나 "API 키", "토큰"처럼 구체적인 이름을 쓴다. 사실 목록의 낱말은 최종 글에 그대로 남으므로, 용어를 풀어 쓴 말이나 직접 만든 정의를 넣지 않는다. 호출하는 쪽은 한국어 문장을 쓰지 않는다.
2. 고정 문장: 그대로 들어가야 하는 문장(사용자 인용, 확정된 문구, 프롬프트 문장)에는 "(그대로 들어갈 문장 — 고치지 말 것)" 표시를 붙인다. 표시가 붙은 블록은 에이전트가 한 글자도 바꾸지 않는다. 사용자 인용은 큰따옴표 안에 한 글자도 바꾸지 않고 옮긴다.
3. 한 번 쓰기: 사실 목록 파일과 아래 프롬프트 양식을 Sonnet 5.5 하위 에이전트에게 넘겨 글을 쓰게 한다(하위 에이전트를 띄우는 방법은 아래 도구별 실행 방법 표에 있다). 하위 에이전트는 그 글의 문체에 맞춰 한국어를 처음부터 쓰고, 영어 문장을 번역하지 않는다.
4. 한 번 교정: 3단계에서 쓴 결과와 같은 프롬프트 양식을 넘겨 Sonnet 5.5 하위 에이전트를 정확히 한 번 더 띄운다. 교정은 한 번만 하며 건너뛸 수 없다. 바뀐 줄이 적다는 이유로 다시 돌리지 않고, 독자 시험 같은 추가 단계도 두지 않는다.
5. 사실 확인: 호출한 쪽이 결과의 숫자, 이름, 경로, 날짜를 사실 목록과 비교하고, 틀린 사실만 고친다. 문장을 직접 다시 다듬지 않는다. 직접 고치면 번역투가 다시 들어온다.
6. 리드가 읽기: 게시하거나 보내기 전에 리드가 문장을 처음부터 끝까지 읽고, 읽었다는 사실을 보고에 적는다. 스크린샷 검수는 그다음에 한다.
7. 증거: 두 번의 호출에 쓴 프롬프트, 결과, 교정 전후 diff를 스크래치패드에 남긴다. 바뀐 줄 비율은 적어 둘 수 있지만 통과 여부를 가르는 기준은 아니다. 작업자가 만든 한국어는 리드가 게시하거나 보내기 전에 이 증거를 확인하고, 증거가 없으면 내보내지 않는다.
8. 이미 있는 긴 파일: 스킬, 규칙 파일, 문서처럼 이미 있는 파일을 교정할 때는 전문을 돌려받지 않는다. `줄 번호: 교정한 줄` 형식으로 바뀐 줄만 받아 스크립트로 반영하고 `diff`로 확인한다. 전문을 돌려받으면 호출한 쪽의 맥락만 불어난다. 2026-09-26에 274줄 파일과 144줄 파일을 전문으로 돌려받았는데, 바뀐 줄은 각각 2줄뿐이었다.

## 도구별 실행 방법

| 도구 | 실행 방법 |
| --- | --- |
| Claude Code | `Agent` 도구를 호출해 하위 에이전트를 띄운다. `model` 옵션은 `sonnet`(Sonnet 5.5)로 고르고 `effort` 옵션은 `low`로 둔다. 하위 에이전트는 설치된 `natural-korean` 스킬에서 팝업과 짧은 진행 보고이면 `references/quick-card.md`와 `references/writing-procedure.md`의 프롬프트 양식만 읽는다. 리포트, 계획, 보고 페이지, 결정 페이지, 문서이면 `SKILL.md`와 `references/` 전체를 Read 도구로 끝까지 읽고 적용한다. 별도의 에이전트 정의 파일은 두지 않는다(2026-10-17). |
| Codex, Gemini CLI | 모델이 설치된 `natural-korean` 스킬 파일을 읽고 1단계부터 8단계까지 같은 순서로 직접 수행한다. 읽는 범위는 팝업과 짧은 진행 보고이면 `references/quick-card.md`와 `references/writing-procedure.md`의 프롬프트 양식만이다. 리포트, 계획, 보고 페이지, 결정 페이지, 문서이면 `SKILL.md`와 `references/` 전체이다. 사실 목록으로 한 번 쓰고 쓴 결과를 한 번 교정한다. 사실은 바꾸지 않는다. |

하위 에이전트 도구가 없는 환경에서는 현재 모델이 쓰기 한 번과 교정 한 번을 직접 수행한다. 스크립트를 실행할 수 없는 환경에서는 체크리스트로 직접 점검하고 자동 점검 스크립트를 실행하지 못했다고 알린다.

## 읽을 것 (지정한 파일과 스킬 파일만)
Read 도구로 끝까지 읽을 파일: <파일 경로>

## 따를 규칙
`natural-korean` 스킬의 규칙과 아래 규칙을 모두 따르십시오. 아래 규칙은 사용자가 정한 한국어 작성 원칙 7가지, "자주 틀리는 꼴" 표와 그 아래 규칙, 문장마다 대어 볼 점검표입니다.

모든 답변은 한국에서 실제로 사용하는 자연스러운 현대 한국어로 작성하세요.

1. 영어 문장 구조를 직역한 표현과 영어식 관용구를 사용하지 마세요.
2. 불필요한 비유, 수사적 표현, 현학적인 어휘를 피하세요.
3. 추상적인 명사보다 구체적인 동사와 직접적인 설명을 우선하세요.
4. 전문적인 내용이라도 한국인 엔지니어가 동료에게 설명하듯 명확하게 작성하세요.
5. 한국어 원어민이 일상적으로 쓰지 않는 표현은 더 자연스러운 문장으로 바꾸세요.
6. 출력 직전에 어색한 번역투와 불필요한 수식을 점검하고 수정하세요.
7. 간결함을 위해 중요한 근거나 기술적 세부사항을 생략하지 마세요.

영어 표현을 그대로 한국어로 옮기지 말고, 한국어 화자가 처음부터 작성한 글처럼 문장을 구성하세요.

### 자주 틀리는 꼴
한국어는 처음부터 한국어로 씁니다. 영어로 생각한 문장을 옮기면 안 됩니다.

| 이렇게 쓰지 말 것 | 이렇게 쓸 것 |
| --- | --- |
| 주어나 목적어를 빼먹음: "우리 코드가 아니었습니다" | "배포가 깨진 원인은 제가 고친 코드가 아니었습니다" |
| 영어 관용구 직역: "시간선이 맞습니다", "요청이 걸리지 않았습니다" | "발생 시점이 일치합니다", "다음 페이지를 불러오지 못했습니다" |
| 사물을 사람처럼: "색이 정보를 나릅니다", "코드가 죽었습니다" | "색으로 상태를 구분합니다", "아무 데서도 쓰지 않는 코드입니다" |

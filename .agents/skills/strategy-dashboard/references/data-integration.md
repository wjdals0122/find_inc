# 데이터 추가와 보존 확인

현재 파일의 형식을 먼저 확인한다. 아래 이름은 이 프로젝트의 기존 구현 예시이며 다른 구조로 바뀌었다면 실제 형식을 따른다.

## HTML 내부 데이터

- `studio-data`는 JSON 원문일 수 있고 `studio-data-gzip`은 gzip 데이터를 base64로 인코딩한 형식일 수 있다. 태그와 데이터 부분을 분리해 읽고 해당 형식으로 다시 저장한다. JSON을 HTML에 내장할 때 문자열의 닫는 script 태그가 HTML 파서를 끝내지 않도록 처리한다.
- `workspace.brands`는 브랜드와 상품 목록, 상품의 `stages.strategy.documents`는 자료 경로를 연결한다. 브랜드만 있는 상태와 상품이 선택된 상태의 라우팅도 확인한다.
- `documents`에는 원문과 제목·경로·분류, `assets`에는 실제 에셋 데이터나 주소, `profiles[brandId][productId]`에는 화면별 요약이 들어 있다. 새 항목의 세 부분을 함께 연결한다.
- `resourceScopes`, `documentScopes`, `assetOrigins`, `pathAliases`가 있으면 실제 구조에 맞춰 새 상품의 소유 범위와 경로를 등록한다. 같은 파일명이나 상대 주소가 다른 상품의 자료로 연결되지 않게 상품별 범위를 유지한다.
- `studio-profile` 같은 초기 프로필이 있으면 기존 초기화 방식을 유지한다. 새 상품의 프로필을 등록하지 않아 이전 상품의 프로필이 대체 표시되는 문제를 확인한다. 기존 기본 상품을 임의로 바꾸지 않는다.
- 히어로와 CTA도 현재 선택된 상품이나 기존 기본 상품에서 자료를 읽는지 확인한다. 새 상품을 추가하려고 다른 상품 ID를 하드코딩하거나 공통 코드를 다시 쓰지 않는다. 실제 구조가 다중 상품을 지원하지 않으면 그 제약을 알리고 가능한 데이터 작업을 완료한 뒤 필요한 기능 변경의 범위를 설명한다.

## 프로필과 원문 대응

- 상품 카드는 확인된 핵심 수치와 조건만 요약한다. 단위·국가·모델·가격 기준일이 다른 값을 같은 비교값처럼 보이지 않게 한다.
- 경쟁 표는 실제 비교 상품 수와 행·열을 맞추고 해당 없음과 미확인을 구분한다.
- 고객 요약은 소유자·시승자·판매자와 구매 전 질문을 구분한다. 대표 고객층으로 검증하지 않은 대상은 가설로 표시한다.
- 브리프는 문서의 메시지별 구매 이유와 한 줄 문구, 근거, 콘텐츠 구성과 제작 가이드를 연결한다. 메시지 수와 장면 수는 원문에 맞춘다.
- 아코디언이 Markdown 제목 정규식으로 내용을 추출하면 실제 제목과 패턴을 대조한다. 렌더링에 필요한 소제목이 없다는 이유로 원본 조사 문서를 임의로 바꾸지 않는다.
- 공식 로고가 없어서 안내 이미지를 넣는 경우 안내라는 점을 대체 텍스트와 설명에 적는다. 템플릿의 기존 브랜드 에셋을 새 브랜드 공식 에셋으로 복사하지 않는다.

## 보존과 검증

작업 전 자료를 파싱해 사본으로 두고, 반영 후 기존 항목의 값이 유지됐는지 비교한다. 기존 브랜드 전체 목록을 새 브랜드 하나로 대체하거나 브랜드의 products 배열을 새 상품 하나로 덮어쓰지 않는다. 공유 브랜드 자료를 수정하면 기존 상품에도 영향이 있으므로 새 상품의 데이터 범위를 우선한다.

스타일과 실행 스크립트는 데이터 태그와 분리해 비교한다. 내용 추가라면 코드는 그대로여야 한다. 동작 검증은 신규 화면뿐 아니라 기존 상품의 라우트, 탭, 검색과 원문 열기도 포함한다. 핵심 연결이 실패하면 실패 범위를 고치고 해당 부분만 다시 확인한다.

검증 출력에는 브랜드·상품 ID와 개수, 누락·깨진 연결, 변경하지 않은 코드의 일치 여부 등 필요한 결과만 남긴다. 원본 HTML 전체나 이미지 base64를 콘솔에 출력하지 않는다. 임시 빌드·브라우저 파일은 최종 산출물과 구분한다.

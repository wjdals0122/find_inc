# Strategy Dashboard

브랜드·상품·경쟁사·고객·마케팅 브리프를 기존 전략 대시보드에 연결한다. 기존 화면에 새 상품 자료를 추가하는 작업이며 별도 요청 없이 디자인이나 기능을 바꾸지 않는다.

## 문서부터 확인

브랜드와 상품을 대화에서 식별하고 `rg --files`로 실제 경로를 찾는다. 다음 다섯 파일이 해당 브랜드와 상품에 맞는지 먼저 확인한다.

| 문서 | 기본 확인 위치 |
|---|---|
| 브랜드 | `01-strategy/brand/<브랜드명>/brand.md` |
| 상품 | `01-strategy/brand/<브랜드명>/<상품명>/product.md` |
| 경쟁사 | `01-strategy/competitor/<브랜드명>/<상품명>/competitor.md` |
| 고객 | `01-strategy/customer/<브랜드명>/<상품명>/customer.md` |
| 브리프 | `01-strategy/brief/<브랜드명>/<상품명>/brief.md` |

- 지정 경로와 기존 구조가 우선이다. 비슷한 이름의 다른 모델·세대·브랜드 문서를 대신 쓰지 않는다. 템플릿에만 들어 있는 예시 자료를 실제 프로젝트 조사 파일로 간주하지 않는다.
- 없거나 비어 있거나 상품이 다른 문서는 파일명·확인 경로와 함께 사용자에게 먼저 알린다. 사용자가 누락 시 중단을 요청한 경우가 아니면 읽을 수 있는 자료로 작업을 계속하고 해당 화면에 자료 없음·미확인을 표시한다. 누락 문서의 조사 내용을 만들어 채우지 않는다.
- 관련 `marketing_messages.md`, 고객 `sources.md`, 에셋과 수집 기록도 있으면 필요한 부분을 읽는다. 문서 원문, 요약과 제안을 구분하고 조사일·가격 조건·출처·인용·가설·광고 여부·미확인을 유지한다. 한국어 요약은 [natural-korean](../natural-korean/SKILL.md)이 필요한 경우 적용한다.

## 원본과 보존 범위

- 수정 대상은 기본적으로 `01-strategy/dashboard/dashboard.html`이다. 작업 전에 현재 파일과 해시, 브랜드·상품 목록, 자료 데이터와 코드 구조를 확인하고 복구할 사본을 임시 위치에 둔다. 작업 중 파일이 바뀌면 최신 변경을 읽고 보존한 뒤 반영한다.
- **현재 dashboard.html을 기준으로 내용만 추가한다.** CSS, 레이아웃, 헤더와 사이드바, 반응형 규칙, 애니메이션, 탭, 검색, 원문 보기, 다운로드와 메시지 선택 기능을 유지한다. 다른 템플릿으로 교체하거나 화면을 새로 만들지 않는다.
- 기존 브랜드·상품의 ID, 순서, 문서, 에셋, 프로필, 링크 매핑과 기본 선택을 유지한다. 같은 브랜드 아래 새 상품이면 상품 항목만 추가한다. 이름이 같아도 다른 모델이면 구분되는 ID를 쓴다. 같은 상품 갱신은 대상 범위만 바꾸며 다른 상품이 공유하는 데이터는 덮어쓰지 않는다.
- dashboard.html이 없으면 그 사실을 알리고 프로젝트의 `01-strategy/dashboard/template.html`을 복사해 시작할 수 있다. 템플릿도 없으면 사용 가능한 자료를 확인하고 대시보드 원본이 필요한 점을 알린다. 존재하는 dashboard.html을 템플릿으로 되돌리지 않는다.
- 템플릿 생성이나 디자인 변경은 별도 요청이 있을 때만 수행한다. 이때도 사용자가 보존하라고 한 원본과 다른 상품 데이터는 유지한다. 실제 콘텐츠가 있는 대시보드와 재사용 예시 템플릿을 혼동하지 않는다.

## 내용 추가

내장 데이터와 렌더러를 수정하기 전에 [데이터 추가와 보존 확인](references/data-integration.md)을 읽는다. 현 파일의 스키마에 맞춰 등록하고 기존 렌더러가 읽는 데이터 필드로 내용을 넣는다.

- 브랜드에는 확인된 정체성과 디자인 규칙, 상품에는 모델·가격 조건·기능·사용 조건·후기, 경쟁에는 비교 조건과 차이, 고객에는 원문과 가설, 브리프에는 메시지별 고객·구매 이유·근거·채널·CTA·콘텐츠 구성·제작 가이드를 연결한다.
- 공식 브랜드 가이드가 없으면 로고·컬러·서체·슬로건을 미확인으로 표시한다. 제작 제안은 공식 규칙과 구분하며 다른 브랜드의 로고·서체·음원을 새 상품의 공식 자료처럼 노출하지 않는다. 템플릿의 캐릭터·음원 예시도 기능 예시임을 표시한다.
- 실제 이미지와 출처를 연결하고 상업적 사용 권한이 미확인이면 유지한다. 로고나 사진이 없을 때는 기존 화면 형식에 맞는 자료 없음 안내를 사용한다. 빈 이미지나 존재하지 않는 파일 링크를 넣지 않는다.
- 메시지를 새로 만들거나 근거를 바꾸지 않고 기존 메시지와 브리프를 대응시킨다. 문서의 제목과 화면 아코디언의 연결 조건을 맞춰 내용이 빠지지 않게 한다. 긴 내용은 기존 원문 보기로 연결하고 카드에는 필요한 요약을 넣는다.
- 원문 링크와 로컬 파일의 상대 경로, 데이터에 내장된 문서·에셋 경로를 구분한다. 출처를 실제로 열 수 있게 연결한다. 가짜 문서 파일을 조사 원본처럼 등록하지 않는다. 누락을 설명하는 화면 메모를 만들면 대시보드용 안내임을 밝힌다.
- 전체 HTML이나 base64 데이터를 출력하지 않는다. 필요한 데이터만 추출하고 키·필드·짧은 코드 구간으로 구조를 파악해 토큰 사용을 줄인다. 새 조사나 프레임워크 설치는 내용을 추가하는 작업에 필요할 때만 한다.

## 수정과 완료

- 피드백이 내용 수정이면 대상 문서와 데이터만 갱신한다. 모델·가격·근거 정정 시 요약, 표, 메시지와 출처 연결까지 대조하고 기존 사용자 편집을 보존한다. 디자인·기능 수정 요청이 명시되지 않았다면 코드 변경으로 해결하지 않는다.
- 저장 전후 CSS와 실행 코드, 기존 브랜드·상품 데이터의 보존 여부를 비교한다. 새 상품의 화면 연결, 원문·이미지, 메시지 선택과 기존 상품 전환을 확인한다. 브라우저를 사용할 수 있으면 데스크톱·모바일 메뉴와 자료 보기를 확인하고 실행 오류를 살핀다. 확인하지 못한 기능은 검증했다고 보고하지 않는다.
- 결과 파일 링크와 추가한 브랜드·상품, 누락 문서와 중요한 미확인 사항, 실제 확인 범위를 짧게 보고한다. 산출물은 아래 절차에 따라 GitHub에 push한다. 웹 게시·Sites 배포는 별도 요청이 있을 때만 수행한다.

## ChatGPT Sites 비공개 배포

사용자가 Sites 생성이나 배포를 요청하면 [비공개 배포 절차](references/private-sites.md)와 현재 제공되는 `sites:sites` 스킬을 읽는다. 로컬 보고서 작성·수정만 요청했다면 이 단계는 실행하지 않는다.

- 완성된 HTML의 디자인·기능과 모든 브랜드·상품 내용을 유지한다.
- 본인만 접근하도록 요청했다면 배포 전후 소유자 전용 권한을 확인한다. 비공개 상태를 확인할 수 없으면 배포를 중단하고 이유를 알린다. 공개 배포로 우회하지 않는다.
- 성공한 배포에서 반환한 실제 웹 주소를 전달한다. URL을 코드블록으로 달라는 요청이 있으면 그대로 따른다.

## 산출물 생성 후 GitHub Push

산출물을 새로 만들거나 수정하고 검증을 마치면 [산출물 GitHub Push 절차](../../../docs/guides/skill-output-git-push.md)를 읽고 따른다. 이번 작업의 산출물과 필요한 관련 파일만 커밋한 뒤 GitHub 작업 브랜치로 push하고, 원격 반영을 확인한 후 완료를 보고한다. 별도 push 승인을 반복해서 묻지 않는다. 파일 변경이 없는 탐색·제안만 수행했다면 빈 커밋을 만들지 않는다.

## 성공 후 완료 알림

요청 범위의 검증과 필요한 GitHub push를 마치면 [공통 완료 알림](../notify-results/SKILL.md)을 읽고 카카오톡 나에게 보내기, 슬랙과 SenderKit 이메일로 핵심 결과와 산출물 링크를 보낸다. 실패하거나 push가 끝나지 않았으면 성공 알림을 보내지 않으며 하위 스킬로 실행한 경우 최상위 작업에서 한 번만 보낸다. 최종 답변에 채널별 전송 상태를 함께 알린다.

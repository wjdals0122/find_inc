# Customer

상품이나 서비스에 관한 고객의 실제 발언을 찾고 사용 맥락과 의사결정을 분석한다. 아래 하위 스킬은 독립적으로도 적용할 수 있는 분석 지침이다. 사용자 요청에 맞는 것만 읽고 조합하며, 네 항목 전체를 요청하면 모두 적용한다.

- [사용 상황 조사](use-context/SKILL.md): 언제, 어디서, 무엇을 하려는지.
- [고객 니즈 분석](customer-needs/SKILL.md): 해결하려는 불편과 원하는 결과.
- [사용 경험 조사](user-experience/SKILL.md): 실제 사용의 장점과 아쉬움.
- [구매 전 우려 조사](purchase-concerns/SKILL.md): 선택을 망설이는 이유와 확인할 조건.

## 범위와 기존 자료

- 대화에서 상품, 브랜드, 모델·버전, 시장, 고객, 경쟁 대상, 요청 단계, 예산과 수량을 확인한다. `rg`로 기존 자료를 찾고 현재 자사 `product.md`, 경쟁 `competitor.md`, 고객 `sources.md`와 `customer.md`가 있으면 관련 부분을 읽는다. 사용자가 자료를 수정했다고 하면 현재 파일을 다시 읽는다. 실제 경로와 사용자 지정 경로를 우선한다.
- 자료 현황과 사이트 추천만 요청하거나 아직 수집하지 말라고 하면 기존 자료에서 확인된 내용과 부족한 내용을 나누고, 추가로 조사할 사이트·주소·수집 항목을 제시한다. 이때 새 본문·댓글·영상 수집, 다운로드와 결과 파일 작성은 하지 않는다. 최소한의 사이트 주소 확인과 기존 자료 읽기는 가능하다.
- 추가 수집을 요청하면 기존 출처를 중복 없이 재사용하고 부족한 고객 자료를 찾는다. 이미 수집이 허용된 경우 별도 승인 단계를 만들지 않는다. 분석만 요청받았다면 지정된 기존 자료를 분석하고 별도 수집을 임의로 시작하지 않는다.
- 수량이 `N건 더`인지 재사용을 포함한 `최대 N건`인지 구분한다. 불명확하면 합리적으로 해석하고 밝힌다. 수량 자리표시자가 남아 실제 상한을 알 수 없으면 필요한 정보를 묻고 그동안 기존 자료 검토를 진행한다. 실제 본문이 확인된 독립 항목만 센다. 댓글은 별도 항목으로 셀 때 원글과 구분하며 중복 원문을 제외한다.
- 최대 건수는 상한이지 조기 종료 이유가 아니다. 특정 건수만큼 채우려고 관련성 낮은 글을 넣지도 않는다. 관련 채널과 부족한 주제를 예산·접근 범위 안에서 충분히 살피고, 표본이 적거나 특정 채널에 치우치면 추가 조사와 한계를 명시한다. 사용자가 표본 부족을 지적하면 기존 건수와 중복을 확인하고 승인 범위 안에서 보강한다.

## 자료 수집

실제 수집에는 [crawler](../crawler/SKILL.md)를 읽고 따른다. 기존 사용자 예산과 유료 실행 금지 조건은 유지한다. crawler를 이용할 수 없으면 가능한 범위를 보고하고, 유료 도구의 비용이나 권한을 확인하기 전 무료로 단정하지 않는다.

- 우리 상품, 직접 경쟁 상품과 이전 세대·대체재를 분리한다. 모델·연식·시장·트림·사용 기간·상황이 확인되지 않으면 미확인으로 남긴다. 과거 세대와 경쟁차 경험을 해당 상품의 사용 경험으로 옮기지 않는다.
- 후기, 게시물, 댓글, 문의, 비교 글과 필요한 영상에서 고객의 원문을 찾는다. 차주·구매자, 구매 예정자, 전문 시승자, 전시장 체험자, 판매자와 광고·협찬 자료를 구분하고 관계나 협찬 여부를 모르면 미확인이라고 쓴다. 판매자의 이해관계는 명시한다.
- 검색 결과 요약, 빈 응답, 읽지 못한 본문과 영상 제목은 원문을 확인한 자료로 세지 않는다. 원문·짧은 발췌·번역·요약·해석을 분리한다. 댓글과 답글은 원글과 바로 위 부모, 직접 주소 및 ID를 남기고 관계를 모르면 추정하지 않는다.
- 기존 자료는 원래 수집 시간을 보존한다. 새로 읽은 시각, 게시일, 수집일은 구분하고 알 수 없으면 미확인으로 기록한다. 저작권과 개인정보 규칙을 따르며 전문 보존이 불가능하면 허용되는 발췌·출처와 이유를 남긴다.

## 분석과 결과물

- 고객이 명시한 사실과 분석자의 해석을 구분한다. 출처가 뒷받침하지 않는 인구통계, 동기, 사용 상황과 구매 의도를 만들어 내지 않는다. 해석이 필요하면 `가설`로 표시하고 그 근거와 확인이 필요한 점을 적는다.
- 실제 발언을 짧고 정확하게 인용하고 각 주장 가까이에 원문 출처를 둔다. 번역과 원문을 구별한다. 전문 리뷰를 장기 차주 의견으로, 단일 사례를 발생률이나 전체 고객의 대표 의견으로 쓰지 않는다. 상반된 경험도 조건과 함께 남긴다.
- 기본 저장 위치는 `01-strategy/customer/<브랜드명>/<상품명>/`이다. 수집 결과는 `sources.md`, 분석은 `customer.md`에 둔다. 사용자가 지정한 경로를 우선하며 분석만 요청된 경우 기존 수집 파일을 임의로 덮어쓰지 않는다. 우리 상품과 경쟁 상품을 구분하고, 수집 기록·실패·비용은 crawler가 요구하는 형태로 연결한다.
- `customer.md`에는 요청된 항목별로 확인된 상황·원하는 결과·긍정 및 부정 경험·구매 전 질문을 정리한다. 인용, 출처, 모델·자료 유형과 한계를 함께 적고 자료 부족이나 표본 편향을 설명한다. 필요한 경우에만 기존 [natural-korean](../natural-korean/SKILL.md)을 적용해 의미와 인용을 보존하면서 문장을 다듬는다.

## 수정과 완료

- 피드백을 받으면 현재 보고서와 자료를 읽고 사용자가 수정한 내용을 보존한다. 조사 대상, 모델, 수량 또는 해석이 바뀌면 관련 인용·출처·집계·가설과 결과를 함께 고친다. 새로 확인한 내용만 확인일을 갱신하고 기존 원문을 임의로 지우지 않는다.
- 사용자 요청과 네 하위 스킬 중 적용한 범위, 원문 인용의 정확성, 로컬·외부 출처 연결, 고객과 전문가 및 경쟁차의 구분, 미확인·광고 표시를 확인한다. 결과 경로와 주요 발견, 수집·재사용 건수, 실패와 표본 한계, 유료 비용을 간결하게 보고한다.

## 산출물 생성 후 GitHub Push

산출물을 새로 만들거나 수정하고 검증을 마치면 [산출물 GitHub Push 절차](../../../docs/guides/skill-output-git-push.md)를 읽고 따른다. 이번 작업의 산출물과 필요한 관련 파일만 커밋한 뒤 GitHub 작업 브랜치로 push하고, 원격 반영을 확인한 후 완료를 보고한다. 별도 push 승인을 반복해서 묻지 않는다. 파일 변경이 없는 탐색·제안만 수행했다면 빈 커밋을 만들지 않는다.

## 성공 후 완료 알림

요청 범위의 검증과 필요한 GitHub push를 마치면 [공통 완료 알림](../notify-results/SKILL.md)을 읽고 카카오톡 나에게 보내기, 슬랙과 SenderKit 이메일로 핵심 결과와 산출물 링크를 보낸다. 실패하거나 push가 끝나지 않았으면 성공 알림을 보내지 않으며 하위 스킬로 실행한 경우 최상위 작업에서 한 번만 보낸다. 최종 답변에 채널별 전송 상태를 함께 알린다.
